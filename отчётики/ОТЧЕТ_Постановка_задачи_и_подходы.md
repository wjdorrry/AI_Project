# 2. Постановка задачи и требования (проект «Sillage&Style»)

## 2.1. Входные данные

Цифровое изображение **образа одежды** (JPEG, PNG, WebP и др.), полученное с камеры смартфона, загрузкой с диска или иного источника.

Дополнительно на вход экспертной подсистемы поступают **структурированные данные интерфейса**:

- множество **активных тегов** образа (цвета, стиль), согласованных со словарём матрицы весов;
- множество **исключённых парфюмерных семейств** (жёсткие ограничения пользователя: «без цитруса», «без кожи» и т.п.).

На этапе учебного прототипа теги могут задаваться **вручную** на странице (имитация ответа модуля компьютерного зрения до подключения реального API).

---

## 2.2. Выходные данные

На выходе пользователь получает **текстовую и числовую рекомендацию** в веб-интерфейсе (без обязательной доработки исходного пиксельного изображения):

1. **Рекомендуемое парфюмерное семейство** — название на **русском языке** (например, «Восточные», «Древесные») и при необходимости служебный ключ на английском (Oriental, Woody) для согласованности с базой знаний.
2. **Краткое текстовое описание** выбранного семейства (объяснение для пользователя).
3. **Итоговый балл** рекомендации — сумма весов матрицы по всем учтённым тегам для победившего семейства (среди семейств, не исключённых ограничениями).
4. **Сводка по остальным семействам** — например, топ нескольких кандидатов с баллами и/или столбчатая визуализация для сравнения.
5. **Индикация исключений** — перечень семейств, полностью убранных из конкуренции из-за настроек пользователя.

Превью загруженного фото остаётся на экране для наглядности; в отличие от задач **сегментации дефектов**, выходом не является новое растровое изображение с наложенными масками, а **семантический результат экспертной системы** и сопутствующая графика интерфейса (карточка, диаграммы).

---

## 2.3. Классы распознавания

Под **классами распознавания** (целевой словарь для модуля анализа изображения) в проекте понимаются **теги образа**, по которым задана матрица весов в файле `PerfumeStyleMatrix.xlsx` / JSON. Каждый тег имеет **строковый идентификатор** в базе знаний (как в датасете/словаре приложения):

**Цвет (категория «Цвет»):**

| Условный индекс | Обозначение в базе (тег) |
|-----------------|---------------------------|
| 0 | Black |
| 1 | White |
| 2 | Grey |
| 3 | Beige |
| 4 | Blue |
| 5 | Brown |
| 6 | Green |
| 7 | Red |
| 8 | Pink |

**Стиль (категория «Стиль»):**

| Условный индекс | Обозначение в базе (тег) |
|-----------------|---------------------------|
| 9 | Sportswear |
| 10 | Evening |
| 11 | Streetwear |

Модель компьютерного зрения (или внешний API) должна **сопоставлять изображение** с **одним или несколькими** такими тегами (постановка **мультилейбл-классификации** или эквивалент через набор меток API с последующим **mapping** на перечисленные имена).

**Целевые «классы» экспертной подсистемы** (не путать с классами CV) — **11 парфюмерных семейств**, для которых в матрице заданы веса: Citrus, Aquatic, Green, Fruity, Woody, Musk, Powdery, Gourmand, Oriental, Floral, Leather. Они **не распознаются** на фото напрямую, а **выводятся правилами** суммирования весов по выбранным тегам одежды.

---

## 2.4. Ограничения этапа

- Обрабатываются **статические фотографии**; потоковое **видео**, выбор ключевых кадров и трекинг образа **не входят** в текущий этап.
- Реализованный прототип веб-приложения работает **локально** в браузере: логика экспертной системы и база знаний выполняются на стороне клиента (**без обязательного бэкенда**).
- Модуль **автоматического тегирования** изображений нейросетью на текущем этапе **может быть заменён** ручным выбором тегов; подключение API (Python-сервер, облако, Hugging Face Inference) относится к **следующему этапу** развития проекта.
- Размер и состав матрицы соответствуют предоставленной методичке (12 тегов × 11 семейств); расширение словаря не меняет общую постановку задачи.

# 3. Обзор и сравнение подходов

## 3.1. Семейства моделей для тегирования образа

Для задачи «изображение одежды → набор тегов (цвет, стиль)» естественны модели **классификации изображений**, а не однопроходные **детекторы объектов** семейства **YOLO**, ориентированные на локализацию множества экземпляров на сцене.

- **Свёрточные сети и ViT (ResNet, EfficientNet, Vision Transformer)** в постановке **мультилейбл-классификации** или нескольких «голов» по атрибутам (цвет / стиль) позволяют обучить или дообучить модель под **фиксированный список тегов**, совпадающий с матрицей.
- **Облачные API компьютерного зрения** (например, Google Cloud Vision — распознавание объектов и меток изображения) дают готовые англоязычные метки; на стороне приложения выполняется **сопоставление** (mapping) меток API с тегами `Black`, `Sportswear` и т.д.
- **Модели с Hugging Face** (в т.ч. специализированные на fashion-атрибутах или обобщённые **image classification**) подходят для прототипа при наличии вычислительного контура (локальный inference или облачный endpoint).
- **Vision–language модели (CLIP и аналоги)** позволяют **zero-shot** сопоставление изображения с текстовыми описаниями тегов; точность зависит от формулировок и может быть ниже, чем у дообученной классификатора под узкий словарь.

**Вывод:** для учебного проекта с жёстко заданной матрицей предпочтительны либо **API с последующим mapping**, либо **мультилейбл-классификатор** под 12 тегов; YOLO имеет смысл только если отдельно поставлена задача **детекции** отдельных предметов гардероба на фото, что усложняет пайплайн и не требуется для текущей матрицы «глобальных» признаков образа.

---

## 3.2. Детекция, сегментация и постановка «теги целого кадра»

- **Детекция (bounding box)** локализует объекты на изображении. Для рекомендации по **общему впечатлению от образа** (доминирующий цвет, стиль) часто достаточно **анализа всего кадра** без разметки каждой вещи.
- **Сегментация** (поклассовая или по экземплярам) даёт маски областей; она полезна, если нужно отдельно оценивать, например, верх и низ или аксессуары. Для текущей базы знаний это **не обязательно** и увеличивает вычислительные и инженерные затраты.
- **Мультилейбл-классификация / тегирование всего изображения** согласована с тем, что матрица весов задаёт вклад **совокупных** признаков образа в парфюмерные семейства.

**Вывод:** для единообразия с экспертной матрицей и простоты прототипа принята постановка **«изображение → множество текстовых тегов из фиксированного словаря»** с последующим **суммированием весов** и учётом ограничений пользователя; детекция YOLO-seg и отрисовка контуров **не являются** обязательной частью постановки данного проекта (в отличие от задачи поиска дефектов дороги).

---

## 3.3. Размещение вычислений

- **Вариант «модель в браузере»** (например, **ONNX Runtime Web**, **TensorFlow.js**) позволяет не поднимать сервер, но требует конвертации весов, продуманного размера модели и может быть **ресурсоёмким** на слабых смартфонах.
- **Вариант «модель на сервере»** (Python + PyTorch / API облака / **Hugging Face Inference**): браузер передаёт файл изображения, сервис возвращает JSON с тегами; клиент только отображает результат и передаёт теги в **экспертный модуль** (который может оставаться на клиенте как сейчас, или дублироваться на сервере).

**Текущий этап:** вычисление рекомендации по матрице выполняется **полностью в браузере** (React); вызов нейросети **отложен**. При подключении ИИ логичен гибрид: **инференс изображения на сервере или во внешнем API**, **правила и матрица** — по возможности без изменений на клиенте.
